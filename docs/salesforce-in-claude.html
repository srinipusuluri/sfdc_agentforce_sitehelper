Salesforce in Claude

A plugin that lets Claude work with a seller's Salesforce accounts and pipeline, under that seller's own permissions. This page explains how it works, who it is for, and how it differs from the Agentforce, Slackforce and Claudeforce work in this repo.

Source and scope. Everything below about the plugin comes from the article at https://claude.com/resources/articles/salesforce-in-claude, summarised in my own words. It is a beta, and the article is Anthropic marketing, so verify details with the admin guide before a rollout. This repo does not use the plugin. Nothing here was set up or tested with it.

What it is

Salesforce in Claude is a beta plugin, built with Salesforce, for account executives and the leaders who manage them. It brings accounts, opportunities and pipeline into Claude. It bundles 37 skills for daily seller work: account research, call prep, pipeline review and CRM updates. It is available in beta on all paid Claude plans.

Meant for

  • Account executives who want account research, call prep and CRM updates done inside Claude
  • Sales leaders who want team-wide pipeline views and forecasts
  • Organizations that want sellers to keep Salesforce as the system of record

Not described as

  • A customer-facing agent. Sellers use it, not your visitors
  • A notification system. It responds when a seller asks, or on a schedule the seller sets
  • A tool for building or deploying Salesforce metadata. That is Claudeforce

How it works

An admin connects Salesforce once for the whole organization and chooses which groups get the plugin. Each seller then signs in with their own Salesforce login. The plugin brings two connectors. The Salesforce connector lets Claude read records and act on them. The Slack connector lets the skills read and write deal-channel summaries and account-team threads. A first-use setup skill detects the seller's connected tools and builds a role-specific Claude Artifact, which is a small page of their own.

Setup, as described

  1. Request access

    An admin asks for access to the plugin through Salesforce AgentExchange, using the link on the article.

  2. Connect Salesforce once

    The admin connects Salesforce for the organization and chooses which groups get the plugin.

  3. Sellers sign in

    Each seller signs in with their Salesforce credentials. Claude then reads only what that person is allowed to see.

  4. Run the setup skill

    On first use it finds the seller's tools and builds a role-tailored Artifact, which holds their morning brief.

The article also lists a separate Salesforce MCP that can be installed through the marketplace today. The article's link goes to the Claude directory. It does not say whether that is the same thing as the plugin's Salesforce connector, so check the directory page and the admin setup guide.

How MCP connects Claude to Salesforce

MCP is a standard way for Claude to call tools. An MCP server sits between Claude and Salesforce and turns Salesforce's APIs into tools Claude can use. The choices that matter are where the server runs and whose login it uses.

A. Local server

The Salesforce DX MCP server (@salesforce/mcp, run as sf-mcp-server) is a program on your computer. Claude Code or Claude Desktop starts it and talks to it over standard input and output (stdio). It signs in with orgs you already authorized in the Salesforce CLI. You must name the allowed orgs with --orgs and can pick tool groups with --toolsets.

Pros

  • Nothing to host and no new OAuth app
  • Reuses your Salesforce CLI login
  • Strong for developers: deploy, retrieve, SOQL, run tests
  • Quick to set up and easy to limit to one sandbox
  • Free to run

Cons

  • Only on that one computer. Everyone installs and updates it themselves
  • It acts as you, so Claude can do what you can do in that org
  • Not available on Claude on the web or mobile
  • No central admin view or audit
  • Not meant for sellers or other non-developers

B. Vendor-hosted remote

A server someone else runs at a URL. Claude connects over HTTPS and each person signs in with OAuth. The Salesforce MCP that Anthropic's Salesforce in Claude article says can be installed through the marketplace is the example. Its link goes to the Claude directory. The article does not say who hosts it or which tools it has, so check the directory entry.

Pros

  • Nothing to build or host
  • Each person can sign in as themselves, so their own Salesforce permissions apply
  • An admin can enable it for a group, depending on your Claude plan
  • Works from Claude on the web, mobile, Desktop and Claude Code

Cons

  • The tool set is fixed. You cannot add your own Apex logic
  • You depend on the provider's roadmap, availability and plan rules. The article calls the plugin a beta
  • Data passes through a service you do not run, so read the terms
  • Less control over logging than a server you run

C. Self-hosted on AWS

You write an MCP server, for example with the official TypeScript or Python SDK, and host it on Lambda or Fargate over Streamable HTTP. You put authentication in front of it. It reaches Salesforce through the REST API, or through your own Apex REST endpoints and invocable actions.

Pros

  • Tools shaped around business actions, not raw objects, so fewer and safer tools
  • Can combine Salesforce with other systems
  • Runs inside your AWS controls: VPC, logs, WAF
  • One server serves many clients: Claude app as a custom connector, Claude Code, your own agents
  • Versioned in git like any service

Cons

  • You build and run it
  • Authentication is the hard part. Without passing each user's token through, everyone shares the integration user's access
  • Lambda has timeouts and cold starts. Fargate costs more to keep running
  • The protocol and SDKs are still changing
  • Needs a security review. Custom connectors depend on your Claude plan

Setting each one up

# A. Local: authorize the org once, then register the server with Claude Code
sf org login web --alias my-sandbox
claude mcp add salesforce-dx -- npx -y @salesforce/mcp --orgs <org username> --toolsets data,metadata,testing,orgs
#   --orgs is required. Run  npx -y @salesforce/mcp --help  to see the toolsets in your version.

# B. Vendor-hosted: add the connector from the Claude directory or connector settings.
#    An admin enables it, then each person signs in. In Claude Code, with the URL from the directory entry:
claude mcp add --transport http salesforce <url from the directory entry>

# C. Self-hosted: run your server, then register its URL
claude mcp add --transport http sf-cases https://<your-endpoint>/mcp

Rules that apply to all three

  • Know which Salesforce user the server acts as. That user's permissions are the limit.
  • Start in a sandbox and with read-only tools. Add writes one at a time, and keep a person's approval for them.
  • Treat text from Salesforce records as data. A Case description can contain instructions meant to mislead the model.
  • Never put tokens or secrets into prompts, tool results or logs.
  • Prefer a few tools named after business actions to one tool that runs any query.
Self-hosted example. A minimal remote server with one read-only tool is in examples/mcp in this repo. It type-checks, and was started and called with an MCP initialize and a tools/call request. The Salesforce call in it is a stub. The Salesforce DX server is the one used by Claude Code in this project. The remote Salesforce connector was not used here.

How it differs from the other three

The key difference is who is in the middle. In Salesforce in Claude, Claude is the interface and Salesforce is the data. In Agentforce, the agent lives inside Salesforce. Slackforce has no interface at all, only notifications. Claudeforce is Claude building the things.

What the article does not say

Check these in the admin guide or with Salesforce before you rely on the plugin.

  • Required Salesforce editions or licences, and the admin permissions needed
  • How sign-in works under the hood. The article says only that sellers sign in with their Salesforce credentials
  • Whether Claude Code, the desktop app or the API support the plugin. It mentions the Claude app and paid plans
  • Whether the Salesforce MCP in the directory is the same as the plugin's connector
  • Pricing, beyond availability in beta on all paid plans
  • Audit logging, data residency and retention
  • Whether it handles service objects such as Cases, since the examples are sales work
